Chapter — Errors and Exceptions

What goes wrong, when Java notices, and how to catch it before it crashes everything.

Every program is one unexpected input away from something going wrong.

A file that isn't there, a number divided by zero, an array index that doesn't exist — Java needs a way to notice these problems and let your program respond gracefully instead of just crashing. That's what errors and exceptions are for.

Code runs ↓ Something goes wrong ↓ Java throws an exception ↓ try/catch intercepts it ↓ Program recovers gracefully
01

What is an error?

An error is something that breaks the rules of the Java language itself — most commonly a syntax error, caught by the compiler before your program ever runs.

Main.java
class Main (
    public static void main(String[] args) {
        System.out.println("Hello world!");
    }
)
Output
Main.java:1: error: '{' expected
class Main (
           ^

Round brackets ( ) were used instead of curly braces { } — the compiler catches this before a single line executes.

Think of it like…A spell-checker on your essay

You type an essay in Word. Before you hand it in, red squiggly lines mark every broken sentence, and you fix them first. Java's compiler works the same way: it reads your whole program before running anything, and refuses to start while grammar mistakes are still in it.

Real life → Java
Your essay→Your Java program
Red squiggly line→Compile error
Fixing it before submitting→Fixing it before the program runs
02

What is an exception?

Even code that's perfectly valid Java can still fail the moment it actually runs. Errors detected during execution are called exceptions.

Main.java
class Main {
    public static void main(String[] args) {
        int num1 = 5;
        int num2 = 0;
        int result = num1 / num2;
        System.out.println(result);
    }
}
Output
Exception in thread "main" java.lang.ArithmeticException: / by zero
    at Main.main(Main.java:5)

This code is syntactically correct — it compiles fine. The problem only appears once Java actually tries to divide by zero.

Think of it like…A recipe that reads perfectly, until you open the fridge

A recipe can be spelled perfectly and every step can make sense. But halfway through cooking you reach “add two eggs” and the fridge is empty. Nobody could have spotted that by just reading the recipe. Only cooking it revealed the problem.

Real life → Java
A perfectly written recipe→Code that compiles fine
Actually cooking it→Running the program
The empty fridge→5 / 0 or a missing file = an exception

04

Unchecked exceptions

Unchecked exceptions mostly happen because of mistakes the programmer made. They're not checked by the compiler — only discovered at runtime. These are also called runtime exceptions.

Main.java
class Main {
    public static void main(String[] args) {
        int[] arr = {1, 2, 3, 4};
        System.out.println(arr[6]);
    }
}
Output
Exception in thread "main" java.lang.ArrayIndexOutOfBoundsException: Index 6 out of bounds for length 4
    at Main.main(Main.java:5)

The code compiles perfectly — the array index is simply out of range, and Java only discovers that while running.

Think of it like…Tripping over your own shoelaces

Nobody makes you fill in a form before walking down the corridor. But if you leave your laces untied and trip, that was a slip in your own steps. Unchecked exceptions are like that: they come from careless code (like asking for item #6 in a list of 4), and the compiler doesn’t warn you in advance.

Real life → Java
Untied shoelaces→Careless code, e.g. arr[6] on a 4-item array
Tripping→ArrayIndexOutOfBoundsException
No form needed beforehand→No try/catch required by the compiler
05

Checked exceptions

Checked exceptions are verified by the compiler before the program runs. If your code might throw one, you must either catch it or declare it with throws, or it won’t compile. They usually come from things outside your program’s control: files, networks, databases, threads.

How to spot a checked exception

Look at its parent. If it extends Exception but not RuntimeException, it’s checked. That’s the whole rule, and it’s why the table above can never be “complete”: every library, and every class you write yourself, can add more.

Common trap

ArithmeticException, ArrayIndexOutOfBoundsException, NullPointerException, NumberFormatException and IllegalArgumentException all sound like things you’d be forced to handle, but they’re unchecked. They aren’t in this table.

What “the compiler forces you” looks like

Thread.sleep() can throw the checked InterruptedException. Ignore it and the program won’t even compile:

Main.java
class Main {
    public static void main(String[] args) {
        Thread.sleep(1000);
    }
}
Output
Main.java:3: error: unreported exception InterruptedException; must be caught or declared to be thrown
        Thread.sleep(1000);
                    ^

Two ways to satisfy the compiler: catch it, or declare it with throws.

Main.java
class Main {
    // Option 1: catch it
    static void pause() {
        try {
            Thread.sleep(1000);
        } catch (InterruptedException e) {
            System.out.println("Interrupted!");
        }
    }

    // Option 2: pass the responsibility to whoever calls us
    public static void main(String[] args) throws InterruptedException {
        pause();
        Thread.sleep(500);
        System.out.println("Done");
    }
}
Think of it like…The school-trip permission slip

Before the bus leaves, the teacher checks every student for a signed permission slip. No slip, no seat on the bus. The school knows trips can have risks (a missing file, a lost connection), so it forces you to have a plan before you go. That is exactly what a checked exception is.

Real life → Java
Teacher checking slips at the bus door→The Java compiler
The signed slip→try/catch or throws
Not allowed on the bus→Code won’t compile

07

Handling exceptions: try / catch

Java uses a try...catch block to handle exceptions.

Syntax
try {
    // body of try block
} catch (ExceptionType variableName) {
    // body of catch block
}

The try block holds code that might throw an exception. The catch block runs only if that exception actually occurs.

Main.java
class Main {
    public static void main(String[] args) {
        try {
            int num1 = 5;
            int num2 = 0;
            int result = num1 / num2;
            System.out.println(result);
        } catch (ArithmeticException e) {
            System.out.println("Denominator can't be 0");
        }
    }
}
Output
Denominator can't be 0
Think of it like…First aid during PE class

During PE everyone runs around, which is the risky part. The nurse sits quietly and does nothing until somebody actually gets hurt. Then she steps in and treats that injury.

Real life → Java
PE class (the risky part)→try block
A scraped knee→An exception is thrown
The nurse treating it→catch block
08

Handling multiple exceptions

Java lets you stack multiple catch blocks to handle different exception types differently.

Syntax
try {
    // body of try block
} catch (ExceptionType variableName) {
    // body of catch block
} catch (ExceptionType variableName) {
    // body of catch block
}
Main.java
class Main {
    public static void main(String[] args) {
        try {
            int[] arr = {1, 2, 3, 4};
            System.out.println(arr[6]);
        } catch (ArithmeticException e) {
            System.out.println("Invalid value");
        } catch (ArrayIndexOutOfBoundsException e) {
            System.out.println("Array index out of range");
        }
    }
}
Output
Array index out of range

Java checks the catch blocks in order and runs the first one whose exception type matches what was actually thrown.

Think of it like…A nurse with a different cure for each injury

Scraped knee? Bandage. Sprained ankle? Ice pack. Anything else? Call the parents. The nurse checks the specific injuries first and the “anything else” rule last. If she checked “anything else” first, the specific treatments would never get used. Order matters in catch blocks too.

Real life → Java
Scraped knee → bandage→catch (ArithmeticException e)
Sprained ankle → ice pack→catch (ArrayIndexOutOfBoundsException e)
“Anything else” → call parents (goes last)→catch (Exception e)
09

The finally block

Beyond try and catch, Java offers a finally block — code that runs no matter what, whether an exception occurred or not.

Syntax
try {
    // body of try block
} catch (ExceptionType variableName) {
    // body of catch block
} finally {
    // body of finally block
}
Main.java
class Main {
    public static void main(String[] args) {
        try {
            int num1 = 5;
            int num2 = 0;
            int result = num1 / num2;
            System.out.println(result);
        } catch (ArithmeticException e) {
            System.out.println("Denominator can't be 0");
        } finally {
            System.out.println("Execution completed");
        }
    }
}
Output
Denominator can't be 0
Execution completed

The division throws ArithmeticException, which catch handles — and then finally still runs afterward, regardless.

Think of it like…Returning the equipment after PE

When PE ends, everyone puts the balls back and lines up for attendance. Doesn’t matter if you played perfectly or got hurt and visited the nurse, the routine happens either way.

Real life → Java
Return equipment + attendance→finally block
Whether you got hurt or not→Whether an exception happened or not
10

Raising exceptions with throw

You can explicitly trigger an exception yourself using the throw keyword.

Main.java
class Main {
    public static void main(String[] args) {
        try {
            throw new ArithmeticException("Denominator can't be 0");
        } catch (ArithmeticException e) {
            System.out.println(e.getMessage());
        }
    }
}
Output
Denominator can't be 0

The instance of the exception, e, has a getMessage() method that returns the exception's message as a String.

Think of it like…Pulling the fire alarm

You don’t wait for fire to find you. The moment you see smoke, you deliberately pull the alarm lever and everyone is alerted. throw is you pulling the lever on purpose.

Real life → Java
Spotting smoke→Your if check finds a bad value
Pulling the lever→throw new …Exception("…")
The message on the alarm panel→e.getMessage()
11

The throws keyword

throws (with an "s") is different from throw — it goes in a method's signature to declare which exception types that method might throw.

Syntax
returnType methodName() throws ExceptionType1, ExceptionType2, ... {
    // body of the method
}
Main.java
class Main {
    static void divideByZero() throws ArithmeticException {
        throw new ArithmeticException("Division with zero");
    }

    public static void main(String[] args) {
        try {
            divideByZero();
        } catch (ArithmeticException e) {
            System.out.println(e);
        }
    }
}
Output
java.lang.ArithmeticException: Division with zero

divideByZero() declares, using throws, that it might throw an ArithmeticException — warning anyone who calls it ahead of time.

Don't mix these up

throw actually triggers one exception, right now, inside a method body. throws just declares, in the method header, what might happen — it doesn't trigger anything by itself.

Think of it like…The “Wet Floor” sign

A yellow wet-floor sign doesn’t make anyone slip, and it doesn’t clean the floor. It just warns everyone who walks past that a slip is possible. throws is that sign, stuck on the front of a method.

Real life → Java
The sign itself→throws in the method header
Someone actually slipping→The exception really being thrown
People walking past, who must be careful→Callers who must catch it
12

Putting it all together

A single flow connects everything in this chapter:

Code runs │ ↓ Something goes wrong │ ↓ Java throws an exception ← or you throw one yourself with `throw` │ ↓ try block catches it │ ↓ catch block runs (first matching type, in order) │ ↓ finally block runs (always, no matter what) │ ↓ Program continues safely

And a method can warn its callers in advance with throws, so the exception doesn't come as a surprise at the call site.

13

Common mistakes

  • ✕ Confusing throw with throws. throw triggers an exception in a method body; throws only declares one in a method's signature.
  • ✕ Assuming every exception needs a throws declaration. Only checked exceptions force this — unchecked (runtime) exceptions don't require it.
  • ✕ Thinking finally is optional "just in case" code. It runs whether an exception happened or not — it's not conditional on the catch firing.
  • ✕ Writing catch blocks in the wrong order. Java checks them top to bottom and uses the first type that matches, so a broader type listed first can swallow a more specific one that never gets reached.

Try it: eight quick challenges

Work each one out yourself before revealing the answer.

Error or exception? Identify the problem
Java
class Main {
    public static void main(String[] args) {
        System.out.println("Hi")
    }
}

A semicolon is missing after println("Hi"). Is this an error or an exception?

An error — a syntax error. The compiler catches this before the program ever runs; it's not something the program discovers at runtime.

Checked or unchecked? Classify it

FileNotFoundException — checked or unchecked?

Checked — the compiler forces you to catch it or declare it with throws before your code will compile.

Guess the output Trace the try/catch
Java
try {
    int[] nums = {1, 2, 3};
    System.out.println(nums[1] / 0);
} catch (ArithmeticException e) {
    System.out.println("Can't divide by zero");
} catch (ArrayIndexOutOfBoundsException e) {
    System.out.println("Bad index");
}

Can't divide by zero — nums[1] is a valid index (2), but dividing it by 0 throws ArithmeticException, which the first matching catch handles.

Guess the output finally always runs
Java
try {
    System.out.println("A");
} finally {
    System.out.println("B");
}

There's no exception here at all. What prints?

A then B — finally runs whether or not an exception occurred, so it still executes after a clean try.

throw or throws? Fill the blank
Java
static void check(int age) ________ IllegalStateException {
    if (age < 0) {
        ________ new IllegalStateException("Age can't be negative");
    }
}

Which keyword goes in each blank?

The method signature needs throws (declaring what might happen); the body needs throw (actually triggering it).

Spot the mistake Catch block order
Java
try {
    int[] arr = {1, 2, 3};
    System.out.println(arr[10]);
} catch (Exception e) {
    System.out.println("Generic problem");
} catch (ArrayIndexOutOfBoundsException e) {
    System.out.println("Index out of range");
}

This won't compile. Why?

Exception is a more general type than ArrayIndexOutOfBoundsException, and it's listed first — the compiler rejects this because the second, more specific catch could never be reached. More specific exception types must come before more general ones.

Try it yourself Write a safe divider

Write a method safeDivide(int a, int b) that divides a by b and prints the result, but prints "Cannot divide by zero" instead of crashing when b is 0.

Java
static void safeDivide(int a, int b) {
    try {
        System.out.println(a / b);
    } catch (ArithmeticException e) {
        System.out.println("Cannot divide by zero");
    }
}
Predict the output Exception message
Java
try {
    throw new ArithmeticException("Out of range");
} catch (ArithmeticException e) {
    System.out.println(e.getMessage());
}

Out of range — getMessage() returns the exact text passed to the exception's constructor.

Chapter recap

Error

Breaks the language's own rules — usually a syntax error, caught before the program runs.

Exception

A problem detected while the program is executing, not while it's compiling.

Unchecked

Runtime exceptions from programming mistakes. No compiler requirement to handle them.

Checked

Compiler-enforced. Must be caught or declared with throws.

try / catch

Risky code goes in try; the response to a specific exception type goes in catch.

finally

Runs no matter what — exception or not.

throw

Triggers one specific exception, right now, in a method body.

throws

Declares, in a method's signature, what it might throw — a warning for callers.

Vocabulary, at a glance

TermMeaning
ThrowableRoot class of the whole hierarchy — anything throwable/catchable.
ErrorSerious, usually unrecoverable JVM/system-level problems.
ExceptionProgram-level problems the code can often anticipate and recover from.
Checked exceptionVerified by the compiler at compile-time; must be handled or declared.
Unchecked exceptionA RuntimeException; only discovered when the program runs.
getMessage()Returns an exception instance's message as a String.
⭐ The easiest sentence to remember

Errors are caught by the compiler before your code runs; exceptions are caught by try/catch while it's running — and throw triggers one, while throws just warns that one might come.
